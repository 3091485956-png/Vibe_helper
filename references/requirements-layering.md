# 需求分层模板（MoSCoW）

## 原则

- **MVP 要小**：Must have 控制在 3–6 个功能，能在合理时间内做完
- 每个功能可独立交付、可验证
- 来源标注：[问卷] / [竞品] / [用户声音]，方便回溯
- 写不出用户故事 = 没想清楚，回去想

## 用户故事格式

```
作为 <角色>，我希望 <做某件事>，以便 <获得某种价值>。
```

## 验收标准怎么写（关键）

**每个 Must have 用户故事必须带 ≥2 条可验证的 acceptance criteria**，
这些标准会在 Stage 8 写完代码后逐条对照打勾——写得含糊 = 最后没法判断做完没。

❌ 反例："页面好看"、"体验流畅"、"响应快"
✅ 正例：
- "输入空内容点提交，按钮禁用并提示'请填写内容'"
- "成功后跳转到 result.html，URL 带任务 id"
- "断网时显示'网络错误，请重试'，不白屏"
- "10 条数据在桌面宽度下不需要横向滚动"

每条 criteria 必须满足：
1. 能一眼判断对错（不需要主观评价）
2. 覆盖至少一个非正常路径（错误/空/边界），不要全写 happy path
3. 是具体行为，不是"系统应该良好运行"这种废话

## 分层定义

| 层 | 含义 | 数量参考 |
|---|---|---|
| Must | 没有它产品不成立，MVP 必做 | 3–6 个 |
| Should | 重要，但 MVP 缺了也能跑 | 5–10 个 |
| Could | 锦上添花，排期看资源 | 越多越好 |
| Won't | 本期明确不做，写下来防 scope creep | 明确列出 |

## 输出格式

```markdown
# 需求分层 · <产品名>

## MVP 范围（Must have）
用户故事 1：
- 描述：作为 <谁>，我希望 <做什么>，以便 <价值>
- 验收标准：
  - <可验证的条件 1>
  - <条件 2>
- 来源：[问卷/竞品/用户声音]
- 依赖：<无 / 依赖 XX>

用户故事 2：
...

## 二期（Should have）
- ...

## 三期（Could have）
- ...

## 本期不做（Won't have）
- 不做 X，原因：...
- 不做 Y，原因：...

## MVP 一句话总结
用上面的 Must have，我们能完成 <核心任务闭环>。
```

## 给用户确认时

> MVP 我建议就做这几件事：<列 Must have>。
> 其他的放到二期/三期。
> 你看这个范围会不会太大/太小？有没有哪些 Must 其实可以砍？
