# 08-评测方案模板，AI 轨道专用

产出语言跟随用户语言：08-评测方案.md 正文用用户的语言，文件名与小节标题保持模板原样。

> 落盘的 08 文档头带版本标记：`> 版本 v1 · <日期> · 基于 00-状态@vN · 变更: 初稿`，版本规则见 `context-assembly.md`。
> 适用前提：Stage 1–2 判定本产品为 **AI 轨道**，即把 AI 拿掉产品不成立或严重残缺。非 AI 产品不产生本文档。

**为什么**：AI 功能，含生成、摘要、检索、对话、Agent，的输出是**非确定的、分级的**，Gherkin 的 Given/When/Then 判不了"摘要写得好不好"。没有评测集，"验收"会退化成"跑一次没报错"；用户的信任会死在上线后第一次一本正经地胡说八道，对应 M8。

**分工铁律：AI 出卷子的结构，人出答案。** agent 负责诊断评什么环节、给表格结构与评分维度草案、配规模与通过线；每一行的**"期望输出"必须由用户填写或批准**。这是评测集里唯一不可无痕外包的单元格，理由有二：期望是产品价值观；自出卷自判卷，考卷会长成模型擅长的样子。

## 第一步：判定需要哪几个集合

绝大多数 vibe coding 产品，即调 API 不训练模型的，只需要两个：

| 集合 | 用途 | 规模 |
|---|---|---|
| 评测集 | 发布门槛：MVP 交付前整集跑完、各环节达通过线 | 见档位表 |
| 冒烟子集 | 每次改 prompt、换模型、调参数后的快速回归 | 从评测集抽 10 例上下，优先含高频与高损 badcase |

**不建训练集或验证集**，那是微调阶段的事。MVP 阶段出现这两个词即跑题。

## 深度档位

| 档位 | 评测集规模 | 评分方式 |
|---|---|---|
| 快速 | ~10 例，一小时能亲手跑完的量 | 人肉逐例，分好、及格、差 |
| 标准，默认 | 30–50 例 | rubric 打分 1–5 加通过率 |
| 深度 | 100+，按输入类别分层 | rubric 加分层通过率，任何一类不许塌方 |

## 环节诊断表，agent 填：链路上什么环节评什么

按 07-技术框架.md 定型的链路逐环节填。**先有架构，才知道评检索还是评生成**：

| 链路环节 | 评什么 | 失败长什么样 | 期望输出谁定 |
|---|---|---|---|
| 例：RAG 检索 | 捞没捞到对的 chunk | 问题相关文档不在 top-k | 用户，给标准答案文档 |
| 例：摘要生成 | 忠实、覆盖、简洁 | 编造原文没有的内容 | 用户 |
| 例：拒答 | 不会时认不认 | 超范围问题硬答 | 用户，列必须拒答的类别 |
| … | | | |

## 评测用例表，本方案的核心交付

输入**必须来自真实来源**：问卷里用户给的真实样例、03 竞品分析"评测种子"小节的竞品短板、04 用户声音的真实差评与真实输入。AI 想象的输入按证据纪律全是 C 级，不许充当主干用例：

| # | 输入 | 来源 | 类别 | 期望输出，人填 | 评分维度 | 版本 |
|---|---|---|---|---|---|---|
| E1 | <真实输入> | 04-用户声音 | 正常 | 待用户填 | 忠实/覆盖 | v1 |
| E2 | <真实输入> | 03-评测种子 | 正常 | 待用户填 | 忠实/覆盖 | v1 |
| E3 | <超长输入> | 对抗，AI 代拟 | 边界 | 不崩、不胡说、优雅降级 | 客观 | v1 |

- **对抗类用例**，含超长、乱码、指令注入、格式怪异，允许 AI 代拟。它们的期望是客观的，即不崩、不胡说、优雅降级，无口味之争
- **委托模式**：期望列允许 AI 预填，但每格标注"默认答案，C 级"；用户改过哪格，哪格升级为其判断。不可无痕外包

## 评分维度草案，全部 C 级，待用户批准后生效

rubric 是产品价值观，宁可短而准还是全而略，agent 只能起草、用户批准：

| 维度 | 1 分 | 5 分 | 状态 |
|---|---|---|---|
| 例：忠实度 | 编造输入里没有的内容 | 全部结论可回溯到输入 | C 级草案 |
| 例：覆盖度 | 漏掉一半要点 | 要点全覆盖 | C 级草案 |
| … | | | |

## 通过线与发布门槛

- 每个环节单独定通过线。例：检索 top5 命中 ≥80%；摘要 rubric ≥3 分的用例占比 ≥85%
- **评测集整集跑完加各环节达线，即 AI 功能的交付条件**，已写入 delivery-checklist
- 冒烟子集任何一例降级，则修复或回滚后重跑，不带伤发布
- 通过线本身是"能力边界"的量化来源：02-brief 的水平线写多少，以评测数据为准。**边界不是写出来的，是测出来的**

## 与 badcase 台账的闭环

上线后每个 badcase：先归因，分 prompt、检索、模型能力、数据、交互五层；修复后**必须回灌成本评测集的新用例**才可关闭，这是"修一个坏一个"的唯一解药，对应 M9。格式与归因分诊表见 Vibe_helper 主 skill 的 badcase-ledger 模板，Stage 8 交接时据此创建 badcase台账.md。

## Common Pitfalls

- **期望列 AI 全代答**：自出卷自判卷，评测集长成模型擅长的样子，考了个寂寞
- **输入全是想象**：想象输入按证据纪律全是 C 级；真实输入去 03/04 的"评测种子"和 01 问卷里翻
- **规模配错档**：快速档塞 50 例没人跑完；深度档 10 例不够分层
- **没有冒烟子集**：评测集建完就死，改 prompt 无回归，等于白建
- **把本文档写成评测教科书**：每一张表都必须是本产品待填的表，没有一页通用方法论。validate.sh 见到"只讲道理不给表"会拦
