## 零、最薄一刀（Thinnest End-to-End Path）— 先写这个

在写任何页面清单和技术选型之前，先用一句话写出"最薄一刀"：

> **一个用户，做一件最小的事，从打开到看到结果，中间不绕路。**

格式：
```
用户打开 <入口> → 做 <一个最小操作> → 系统返回 <一个最小结果>
```

例子：
- ✅ "用户打开页面 → 粘贴一段文字 → 点按钮 → 看到摘要"
- ❌ "用户打开页面 → 注册 → 登录 → 上传文件 → 配置参数 → 看仪表盘"（这不是一刀，是五刀）

**开发阶段必须先把这一刀端到端打通**，其他 Must 功能、空状态、错误处理都在这之后补。
如果这一刀打不通，后面全是空中楼阁。写不出最薄一刀 = 还没想清楚 MVP 到底是什么，回去想。

## 一、产品框架（`06-产品框架.md`）

### 1. 信息架构

列出所有页面/模块及层级，画出树形结构：

```
<产品名>
├── 落地页
├── 登录/注册
├── 主界面
│   ├── <核心功能区 A>
│   ├── <核心功能区 B>
│   └── 设置
└── <结果/输出页>
```

只列 Must have 涉及的页面，Should/Could 标注"(二期)"。

### 2. 用户流程

核心任务走查：从用户打开产品到完成最关键任务，每一步点什么、看到什么。

```
打开 → 落地页 → 点"开始" → 登录（可选） → 主界面
  → 点击 <核心操作> → 填写 <输入> → 点击生成
  → 等待 → 看到 <结果> → 可 <导出/分享/再试一次>
```

每个分支（空状态、错误、首次使用）都要覆盖一句。

### 3. 关键页面元素清单

每个 Must 页面写清楚：

```
## 页面：<名称>
- 目的：<这个页面是干嘛的>
- 主要元素：
  - 顶部：...
  - 主体：...
  - 底部/操作区：...
- 关键交互：<点哪发生什么>
- 空状态：<第一次用什么都没有时显示什么>
```

## 二、技术框架（`07-技术框架.md`）

### 1. 架构总览

分层描述：

```
[前端]  ↔  [API/后端]  ↔  [数据存储]  ↔  [外部服务/第三方 API]
```

### 2. 具体选型

每一项写：选什么、为什么、备选是什么。

| 层 | 选型 | 选择理由 | 备选 |
|---|---|---|---|
| 前端框架 | 例：React / Vue / 原生 | 为什么 | Svelte / Solid |
| 样式 | 例：Tailwind | 为什么 | CSS 模块 / antd |
| 后端 | 例：Node + Fastify / Python FastAPI / 纯静态 | 为什么 | Next.js API Routes |
| 数据库 | 例：SQLite / Postgres / 无需 DB | 为什么 | Supabase |
| 认证 | 例：Magic link / 无登录 / OAuth | 为什么 | Auth0 |
| 部署 | 例：Vercel / Cloudflare Pages / 单机 Docker | 为什么 | 自有 VPS |
| 关键第三方 | 例：OpenAI API / 云存储 | 为什么 | |

#### 选型理由：好 / 坏对照

理由必须落到**本产品的具体约束**上，不是行业口号：

❌ 坏例："前端选 React，因为生态好。"（哪个功能用到了"生态好"？和其他候选的差距在哪？）

✅ 好例："前端选 React：需要虚拟列表 + 图表两个成熟库（对应 Must F3/F5）；备选 Vue3（更轻，但图表生态弱一档）；不选 Svelte：个人维护风险大于 F3 带来的收益。"

### 3. 关键技术难点

从竞品分析里找参考：

```
难点：<例：文件解析大文件会卡>
竞品怎么做：<谁做过、他们怎么解决的>
我们的方案：<...>
风险：<...>
```

### 4. MVP 开发顺序建议

严格按依赖关系排，不要跳步（vibe coding 最常见的翻车就是先画漂亮 UI，后补数据层，结果全部返工）：

1. **项目骨架 + 部署管道**：先把空壳能部署上去
2. **数据模型 / 存储方案**：表结构、字段、关系先定死，后面不许改
3. **最薄一刀端到端打通**：一个能跑的 happy path（哪怕 UI 丑）
4. **补其他 Must have 功能**
5. **补 UI、空状态、错误状态**
6. **过交付 checklist**（见 `delivery-checklist.md`）

### 选型纪律

- **优先成熟栈**：社区大、文档全、自己熟。不为了学新技术在产品里赌。
- **能不做后端就不做**：MVP 能用静态 + 第三方 BaaS 解决，就别自己搭服务器。
- **每个选择都要有理由**：写不出理由 = 在拍脑袋。

## 三、08-评测方案（AI 轨道时必产，模板见 `references/eval-plan.md`）

**为什么在 Stage 6 而不是更早**：链路定型后才知道要评什么——有没有检索、分不分环节，写在 07 之前全是猜（M6 同理）。**为什么必须**：AI 类 Must 的质量验收（05 里的评测引用）指向本文档；没有它，AI 功能的验收退化成"跑一次没报错"（M8）。

agent 分工（AI 出卷子的结构）：诊断链路上哪些环节评什么、给用例表结构与评分维度草案、配档位规模与通过线建议。
用户分工（人出答案）：填/批每一行"期望输出"、批准 rubric、拍通过线——期望列是产品价值观，不可无痕外包（委托模式可预填，标注"默认答案（C 级）"）。

输入来源不许凭空想象：01 问卷的真实样例 + 03"评测种子" + 04 的真实差评。对抗用例（超长/乱码/注入）可 AI 代拟。
