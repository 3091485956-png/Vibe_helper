# Tech Framework — 产品框架与技术框架

把"做什么"翻译成"怎么做"：页面长什么样、用什么技术、**按什么顺序开发**。产出直接决定开发会不会返工。

在 Vibe_helper 全流程中对应 Stage 6；单独使用时本 skill 独立完成。

## 输入

- `05-需求分层.md` 的 Must 清单（最佳）；没有就先问"第一版必做的功能是哪几个"
- `02-brief.md`（约束与偏好：平台、技术栈倾向）
- `03-竞品分析.md`（可选）：竞品用什么栈、踩过什么坑，难点解法优先从这里找
- 什么都没有 → 先问产品形态（Web/App/插件）+ Must 功能，再开工

## 深度档位（开场确认，默认标准）

| 档位 | 产出 |
|---|---|
| 快速 | 最薄一刀 + 一张选型表（选型/理由/备选）+ 开发顺序 |
| 标准 | 完整产品框架 + 技术框架（模板见 references） |
| 深度 | 完整框架 + 每项选型两个备选深评 + 技术风险清单（概率/影响/缓解）+ 成本估算 |

## 步骤

1. **先写"最薄一刀"**（必须第一个写）：一个用户做一件最小的事，从打开到看到结果。写法与好坏例见 `references/framework-output.md`。"注册→登录→上传→配置→看仪表盘"不是一刀，是五刀。**写不出最薄一刀 = 还没想清楚 MVP，回去想**
2. **产品框架** `06-产品框架.md`：信息架构（树形，只列 Must 页面）、用户流程（含空状态/错误/首次使用分支）、关键页面元素清单
3. **技术框架** `07-技术框架.md`：架构分层；选型表每行**选型/理由/备选**——理由必须落到本产品的具体功能上（"需要虚拟列表+图表库所以 React"，不是"生态好"）；关键技术难点优先参考竞品怎么做；开发顺序严格按依赖：骨架可部署 → 数据模型定死 → 最薄一刀打通 → 其他 Must → UI/状态
4. **选型过目**：选型表给用户看一次，用户想换就改，回"你定"按推荐走——技术栈是用户偏好，不替用户拍板

## Common Pitfalls

- **跳过最薄一刀直接铺页面**：没有端到端路径的架构是空中楼阁
- **选型理由是口号**："生态好、社区大"没有落到本产品的哪个功能
- **为炫技选冷门栈**：优先成熟、社区大、用户自己 hold 得住的；MVP 能静态 + BaaS 就别自建后端
- **开发顺序乱排**：先画 UI 后定数据模型 = 全部返工；数据模型先定死，后面不许改
- **页面清单混入 Should/Could**：框架阶段只覆盖 Must，二期的标"(二期)"即止
- **忽略竞品已踩过的坑**：难点先查 Stage 3 记录，别自己发明解法

## 输出物

- `06-产品框架.md`
- `07-技术框架.md`（含最薄一刀 + 选型表 + 开发顺序）
