# User Voice — 用户声音挖掘

不是写综述，是回答一个致命问题：**这个需求是真的吗？用户到底在骂什么、夸什么、为什么掏钱？**

在 Vibe_helper 全流程中对应 Stage 4；单独使用时本 skill 独立完成。

## 输入

- 竞品名单：优先读 `00-状态.md` 的确认对标集合，其次 `03-竞品分析.md`；都没有就直接问用户"查哪几个竞品"
- 目标用户画像（没有就问一句：你的用户是谁、混在哪些社区）

两者都没有 → 先跟用户确认竞品名和用户群，再开工。

## 深度档位（开场确认，默认标准）

| 档位 | 渠道数 | 范围 |
|---|---|---|
| 快速 | 2 | 竞品评论区 + 1 个社区，够做需求真伪初判 |
| 标准 | 4 | 评论区 + 技术社区 + 中文社区 + GitHub Issues |
| 深度 | 6+ | 标准范围 + 中英文社区 + 抱怨的时间线对比 |

## 步骤

1. **按渠道搜**：来源优先级与搜索词模板见 `references/user-research.md`（App Store/Google Play/Chrome Web Store/G2 → Reddit/HN/V2EX/即刻 → 知乎/小红书 → GitHub Issues）
2. **真读帖子**：每个引用的帖子/评论本轮真实打开，转述与原帖不符 = 违规
3. **按主题归类提炼**（不是逐条罗列）：反复抱怨（≥3 独立来源 = 高优机会）、自发夸的、**workaround**（用户在用什么凑合——那就是直接竞争对手）、付费意愿信号。判断信不信看**行为证据**：有人付费/花时间绕过 = 需求为真；只有嘴上说想要 = 存疑
4. **写报告** `04-用户声音.md`：第一屏决策面板 → 机会点（证据+行为证据+对我们的启示）/ 价值点 / 空白点 / **需求真伪初判** / 用户原话摘录 / **评测种子（AI 轨道时：用户被坑过的真实输入 = 评测集主干用例）** / 待核实清单。好/坏洞察对照见 references
5. **汇报时给判断**：需求真伪初判必须给（真需求/存疑/假需求 + A/B/C 证据等级）。如果证据指向"没人讨论、没人凑合、没人付钱"，**明确说出来**——单独使用本 skill 时的产出就是"这个方向值不值得做"的证据包

## 证据分级与幻觉显性化纪律

全文遵守 `references/anti-hallucination.md`：论断标 A（有证据）/ B（证据+推理链）/ C（模型推测，进待核实清单）；每条洞察 ≥2 个独立来源才算数（单条轶事标"待验证"）；链接本轮真实打开，落盘前随机抽 5 个溯源复核；禁止编评论；区分用户的**抱怨**（事实）和**建议**（意见）；末尾强制"待核实清单"。

## Common Pitfalls

- **把"想要"当需求**：嘴上说要 ≠ 会用；只有行为证据（付费/绕过/花时间）才算数
- **单条轶事当趋势**：一个帖子骂得凶就写"用户普遍不满"
- **编评论/编原话**：搜不到就写"本轮未覆盖，建议补充 X 渠道"
- **只罗列不归类**：20 条摘抄不是洞察，按主题归并后给出"所以我们该做什么"
- **只看差评**：用户为什么留下来（价值点）决定我们不能丢什么
- **忽略中文/英文一边**：两边用户抱怨的维度常不同
- **AI 轨道漏标评测种子**：用户被坑过的真实输入是评测集最珍贵的主干用例，想象输入全是 C 级不许充数
