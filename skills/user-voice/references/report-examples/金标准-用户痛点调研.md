# 理工科学生论文复现与写作痛点调研报告

——基于公开一手资料的用户调研与产品设计建议（2026年9月）

## 摘要

本报告聚焦理工科学生"复现论文"这一核心场景，基于知乎、CSDN、arXiv实证研究、科学网、高校复现黑客松报告、抖音/小红书学生真实吐槽等公开一手资料，梳理学生在写论文与复现论文全流程中的真实痛点。核心发现：复现失败不是学生能力问题，而是系统性交付物缺失——公开R代码补充包仅25.9%能无错运行，18篇带artifact的论文中无一篇被独立团队完整复现，旧版PyTorch代码在新环境报错率高达93%。报告进一步将复现需求按用户技术成熟度、复现旅程阶段、KANO层级三个维度分层，并据此推导产品功能设计。

## 一、调研方法与数据来源

本报告所有痛点均有公开一手来源支撑，不依赖臆测。来源覆盖五类材料：学生在社交平台的真实吐槽、同行评审的复现失败实证研究、高校复现黑客松的学生反馈统计、官方媒体观察，以及现有AI科研工具的能力评测。

### （一）学生真实吐槽

采集知乎、CSDN、抖音、小红书等平台研究生对"复现论文"的描述性发言与求助帖，用于捕捉产品的"关键时刻"。

### （二）学术实证研究

引用已发表的复现性量化研究：NLP复现阻塞因素频次调查、R代码补充包自动化运行率、软件工程实证研究复现尝试、MRI复现黑客松总结，用于给痛点定量。

### （三）高校复现黑客松报告

瑞士SwissRN 2025计算复现黑客松、大学图书馆复现黑客松、课堂数据复现教学实验，直接记录学生复现时遇到的具体技术障碍。

### （四）官方与媒体观察

科学网"4年打假"报道、中科院科学数据共享评论、光明网毕业论文调查、高校研究生心理课程报道，用于交叉验证学生主观感受与官方观察。

## 二、复现论文痛点（核心场景）

把所有来源的痛点归并后，复现障碍不是某一个技术问题，而是一条从"拿到论文"到"跑出一致指标"的长链条，每一环都可能卡死。以下六大痛点按严重程度排列。

### （一）痛点一：环境配置地狱——90%的复现死在依赖版本上

学生从GitHub clone代码后，第一步装依赖就可能卡死数天。

高频引述："90%的代码复现失败源于依赖版本冲突"——作者可能用Python 3.6+Torch 1.8，学生本地是Python 3.10+Torch 2.0。

量化数据：PyTorch 1.8代码在2.0+环境直接报错率93%；CUDA 11.6编译的kernel在RTX 40系显卡崩溃率77%；Python包版本冲突导致程序异常的比例达65%。

学生分不清NVIDIA Driver、系统CUDA Toolkit、PyTorch Runtime三层概念，光排查就要数小时。

2026年新代码默认在H100/A10上跑，实验室只有RTX 4090，FlashAttention等算子必须降级兼容。

Docker被公认为复现金标准，但写Dockerfile和管理镜像是软件工程技能，大多数科学家从未学过。

### （二）痛点二：代码本身就是坏的——不是你的错，但你得修

即使环境配对了，代码也常常不能直接运行。多项独立研究给出了触目惊心的成功率。

86篇文章中仅5篇提供了可复现的研究artifact，而这5篇中没有一篇能被完全复现——2篇部分可复现，3篇不可复现。（arXiv:2510.25506）

对OSF上R代码补充包的自动化重建：仅25.87%的R脚本在Docker容器中无错误完成。（arXiv:2505.21590）

300个AI生成项目实证：仅68.3%能按指定依赖成功执行；52.6%的失败源于代码本身生成错误。（arXiv:2512.22387）

MRI图像重建复现hackathon学生报告：README几乎无指导、requirements省略包版本、复数值loss处理缺失、代码库充斥注释掉的片段和不工作的占位符。（arXiv:2601.18314）

### （三）痛点三：指标对不上——跑通了，但数差一大截

这是最摧毁学生自信的一环：代码不报错了，但论文报告的精度就是复现不出来，而且没人告诉你差在哪。

真实学生自述：给师兄打电话要源码被推脱"硬盘丢了"，只能逐行重写，熬了整整7天，最后指标还差20个点；"我当时觉得为什么我做不出来，难道我的科研天赋为零吗？"

常见原因：随机种子未固定、batch size作者开到8192（实验室显卡撑不住）、用TPU/A100而实验室只有V100、不同GPU架构浮点精度差异。

独立复现hackathon：8张图因代码里的文件路径与下载后目录结构不一致而失败；函数需要补全论文未说明的参数。

### （四）痛点四：数据/资源获取——数据集找不到、下不动、版本对不上

代码有了，环境好了，但数据拿不到或拿错版本，复现照样进行不下去。

百度网盘已成为国内论文附件的事实分发渠道，但非会员下载限速50至100KB/s，2GB文件要数小时；分享链接随时可能失效。

瑞士SwissRN 2025复现黑客松评分：数据可访问性与数据版本化并列最重要。即使数据技术上可访问，缺失的元数据、不清楚的预处理步骤仍构成巨大障碍。

实验类学科（化学/生物/材料）更甚：绝大多数期刊不要求作者提供原始数据，仅凭论文中的实验步骤，许多研究无法被同行重复。

### （五）痛点五：学术传承断裂——师兄毕业，知识跟着蒸发

在国内实验室，复现"师兄师姐的毕业论文"是研一研二的家常便饭。但隐性知识不随论文留存，人走了就断了。

真实案例：复现师兄毕业论文要原始数据和模型，师兄说毕业后就删完了，再联系已被拉黑。

更荒诞的案例：师兄自己被问到时说"我开始也做不出来，后来不知道什么情况突然就做出来了，他也不知道咋回事"。

人大博士陈路花4年复现领域内"开山之作"，最终复现报告证明该论文结果是编出来的——学生花数年在错误地基上盖楼。

### （六）痛点六：时间成本与心理内耗——复现本身就是消耗战

前面每一个技术障碍，最终都折算成学生的时间和情绪。

Baseline复现半个月跑不出来是常态；"你根本不知道自己做的东西到底还能不能发"。

上交大学术之星自述两大困难：实验反复失败很久没有积极反馈，容易焦虑和自我怀疑；技术瓶颈，现有方法不够用。

高校为工科研究生专开解压课，总结四大内耗：科研瓶颈期自我否定、多重压力下选择纠结、完美主义因小偏差反复返工、孤独科研。

## 三、论文复现需求分层

基于上述痛点，本节将复现场景的用户需求按三个维度进行分层：按用户技术成熟度分层、按复现旅程阶段分层、按KANO需求层级分层。三个维度交叉构成完整的产品需求地图。

### （一）按用户技术成熟度分层

不同年级、不同技术背景的学生，在复现时面临的核心障碍和需要的支持截然不同。

| 层级 | 典型用户 | 核心障碍 | 最需要的支持 | 产品切入点 |
|---|---|---|---|---|
| L1 入门层 | 研0/研一，首次复现论文；不会配CUDA、没读过完整工程代码 | 环境装不上、不知道从哪下手、看不懂README | 保姆式引导：一键环境、逐步执行、报错直接给修复命令 | 云端Notebook + 步骤导航 + 报错一键修复 |
| L2 进阶层 | 研二，能跑通baseline但调不动指标；做过若干复现 | 指标差几个点找不到原因、不知道哪个超参/预处理影响结果 | 诊断归因：指标对比、差异分析、消融建议 | 复现诊断面板 + 实验记录 + 指标对账 |
| L3 资深化 | 博二以上，要做改进实验、SOTA对比、写复现报告 | 多论文横向对比、实验管理混乱、复现结果不可信 | 实验管理、复现对比、社区协作、可信度验证 | 实验管理平台 + 复现对比 + 可复现性评分 + 社区 |

### （二）按复现旅程阶段分层

学生从决定复现一篇论文到完成复现并产出结果，经历五个阶段，每个阶段的需求和阻塞点不同。

| 阶段 | 用户在做什么 | 核心阻塞 | 对应痛点 | 阶段需求 |
|---|---|---|---|---|
| 1. 决策期 | 判断这篇论文值不值得花一两周复现 | 不知道代码能不能跑、数据能不能拿到、前人复现过没有 | 痛点二、五 | 可复现性评分、前人复现记录、踩坑预览 |
| 2. 准备期 | 找代码、下数据集、配环境 | 环境地狱、数据下载慢/失效、依赖版本冲突 | 痛点一、四 | 一键云端环境、数据聚合仓、依赖自动解析 |
| 3. 执行期 | 跑通代码、debug报错 | 代码bug、路径错误、缺参数、看不懂报错 | 痛点二 | 步骤导航、报错诊断、代码考古辅助 |
| 4. 调优期 | 指标对账、归因差异、做改进 | 指标差几个点不知道为什么、随机种子/batch size/硬件差异 | 痛点三 | 指标自动对比、差异归因、消融建议 |
| 5. 沉淀期 | 记录实验、写论文实验章节、分享经验 | 实验记录散乱、写实验章节痛苦、经验无法传承 | 痛点六 | 自动实验记录、实验章节草稿生成、复现页面沉淀 |

### （三）按KANO需求层级分层

按KANO模型将复现相关需求分为基本型、期望型、兴奋型三层，指导产品优先级。

| 需求层级 | 定义 | 具体需求项 | 不满足的后果 | 满足后的效果 |
|---|---|---|---|---|
| 基本型需求（必须有） | 没有它产品就不可用，用户不会考虑第二次 | 云端一键复现环境；代码能直接跑；数据集/权重可下载；报错有明确指引 | 产品直接不可用，用户流失 | 用户觉得"本该如此"，不会特别惊喜 |
| 期望型需求（做得越好越满意） | 做得好用户满意度线性上升，是核心竞争点 | 指标自动对比与归因；复现步骤拆解；实验配置自动记录；文档缺漏智能补全 | 用户勉强能用但吐槽多 | 用户明确感知到效率提升，愿意付费/推荐 |
| 兴奋型需求（差异化惊喜） | 用户没预期到，做到了会成为口碑 | 论文可复现性评分；社区踩坑地图；自动生成实验章节；复现失败率大数据洞察 | 用户无感知（本来就没期待） | 用户"哇"一下，形成传播和留存 |

### （四）三维交叉：核心功能需求矩阵

将三个维度交叉，可以得到产品MVP阶段应优先满足的需求集合。下表列出每个交叉格的关键功能项，用于指导排期。

|  | L1 入门层 | L2 进阶层 | L3 资深化 |
|---|---|---|---|
| 决策期 | 论文选择推荐（标星高、易复现） | 可复现性评分对比 | 复现率大数据洞察、选题风险评估 |
| 准备期 | 一键云端环境（零配置） | 依赖版本自动迁移建议 | 团队环境模板共享 |
| 执行期 | 步骤导航+报错一键修复 | 报错根因分析、代码考古 | 多仓库对比、实验管理 |
| 调优期 | 指标跑通即成功 | 指标对账与差异归因 | SOTA横向对比、消融实验辅助 |
| 沉淀期 | 一键生成复现笔记 | 实验章节草稿生成 | 复现报告、社区分享、传承给下届 |

## 四、写论文痛点（简述）

用户明确标出复现为重点，但写论文的痛点不能忽略——它和复现共用同一批用户、同一段工作流。

选题与创新点空转：觉得什么都有人研究过，方向太大或太小，与导师沟通不畅。

文献读了但串不起来：被动"信息搬运"，划线抄录却不批判、不思考与自身研究的关系。

学术语言与结构不过关：理工学生常年写实验报告，专业语言困难，初稿结构松散、不符合IMRAD规范。

心理层面执行瘫痪：空白恐惧、结构混乱、拖延、完美主义，将写作"灾难化"导致行动力瘫痪。

## 五、现有工具的缺口

学生并非没有工具可用，但现有工具各自只解决流程中的一段，且关键能力仍不成熟。

| 现有方案 | 能做什么 | 关键缺口 |
|---|---|---|
| Papers With Code | 找论文对应GitHub仓库、SOTA榜单 | 只做索引，不解决环境能不能跑、数据能不能下、指标对不对得上 |
| 通用大模型 | 解释论文、解释报错、写代码片段 | 不能在真实GPU环境把代码跑起来；会幻觉编造文献；写的Discussion可能超出数据支撑 |
| Docker/Conda | 理论上可复现 | 是软件工程技能，多数学生没学过；写Dockerfile、处理GPU/CUDA三层关系门槛高 |
| AI Coding Agent | 补全代码、改bug | 仅68.3%生成项目能跑通；缺乏元认知闭环，不能持续质疑结论、根据新证据调整方向 |
| 实验管理工具 | 记录实验指标、对比实验 | 解决"我跑了什么"，不解决"论文为什么跑不出来"；上手成本高 |
| 网盘/手动传数据 | 分发数据集 | 限速、链接失效、版本不明；学生为下数据集要找破解工具、拼提取码 |

## 六、产品功能设计建议

基于上述痛点与需求分层，产品核心定位为面向理工科学生的"论文复现工作台"：输入一篇论文或一个GitHub仓库，产品负责把它从"PDF+代码"变成"你这边能跑出一致结果"，并在过程中沉淀实验记录、辅助写出论文实验章节。

### （一）核心功能模块

功能1：一键复现环境（云端GPU，本地零配置）
对应痛点：环境配置地狱（90%复现死在依赖冲突）。粘贴arXiv链接或GitHub仓库，自动解析requirements/environment.yml/Dockerfile，逆向推断缺失依赖，在云端拉起预装正确CUDA/PyTorch版本的容器。对2026年新代码要求H100而学生只有4090的情况，自动提示并做算子降级兼容。

功能2：复现诊断面板（自动定位"差在哪"）
对应痛点：代码是坏的、指标对不上。自动跑代码并逐段诊断环境错误、代码bug、未声明参数、文件路径错误；跑通后自动与论文报告指标对比，输出差异归因提示。

功能3：论文资产聚合仓（数据+模型+超参一站式）
对应痛点：数据找不到、下不动、版本对不上。按论文聚合GitHub仓库、数据集、预训练权重、超参、随机种子、预处理脚本；对百度网盘/失效链接做镜像与多源备份。

功能4：复现步骤导航（论文方法→可执行步骤拆解）
对应痛点：代码难读、实验迷路。用LLM把论文Method章节拆解为有序步骤，每一步标注对应代码文件与行号、输入输出、预期中间结果。

功能5：复现社区与"踩坑地图"（人走了，经验留下）
对应痛点：学术传承断裂。每篇论文一个公开复现页面，学生可登记"我卡在哪、怎么解决、最终指标多少"，形成踩坑记录与指标水位线。

功能6：实验记录与论文写作联动
对应写论文痛点：结构松散、数据不支持结论。自动记录每次运行的配置与指标，生成实验表格与消融图；基于真实跑出的数据自动生成实验章节草稿，并标注结论成立条件。

功能7：论文可复现性评分（上线前先看能不能跑）
对应痛点：代码质量参差、踩雷成本高。自动给论文打分：是否有官方代码、依赖是否完整、数据是否可访问、社区复现成功率、指标水位线分布。

### （二）功能优先级

| 优先级 | 功能 | 理由 |
|---|---|---|

### （三）学生使用旅程

第1步 输入论文：粘贴arXiv链接，产品先跑可复现性评分，告诉学生"这篇能不能复、大概要踩哪些坑"。
第2步 环境就绪：自动装好依赖、拉好数据，学生打开Notebook直接运行，无需本地装CUDA。
第3步 跟着导航跑通：按Method拆解步骤逐步执行；报错时诊断面板定位原因并给修复建议。
第4步 指标对账与改进：与论文指标自动对比，差异归因；实验配置自动记录，方便做消融和改进。
第5步 沉淀与写作：一键生成实验章节草稿与图表；复现记录沉淀到论文页面，成为下一个学生的起点。
