# Requirements Layering — 需求分层（MoSCoW + Gherkin + RICE）

回答两个问题：**第一版做什么、不做什么？先做哪个？**这是防止 MVP 越做越大的第一道防线。

在 Vibe_helper 全流程中对应 Stage 5；单独使用时本 skill 独立完成。

## 输入

- 功能清单：来自 `02-brief.md`，或用户口述/贴出来的一份功能列表
- 可选增强：`03-竞品分析.md`（竞品功能对比）、`04-用户声音.md`（哪些痛点证据强 → RICE 的信心分）
- 只有想法没有清单 → 先让用户把脑子里的功能全部倒出来（不排序不评判），再开始分层

## 深度档位（开场确认，默认标准）

| 档位 | Must 数 | 验收场景 | RICE |
|---|---|---|---|
| 快速 | ≤4 | 每故事 2 个场景 | 不打分 |
| 标准 | 3–6 | 每故事 2–3 个场景 | Must 内部打分 |
| 深度 | 3–6 | 每故事 3–5 个场景 | Must + Should 打分，输出排序理由 |

## 步骤

1. **MoSCoW 分层**：Must（没有它产品不成立）/ Should（缺了也能跑）/ Could（锦上添花）/ **Won't（明确不做，写原因）**。每个功能标来源：[问卷/竞品/用户声音]
2. **用户故事**：每条 Must 写成"作为 \<角色\>，我希望 \<动作\>，以便 \<价值\>"，标依赖
3. **Gherkin 验收场景**：每条 Must ≥2 个场景，格式与好/坏对照见 `references/requirements-layering.md`：
   ```
   - 场景：空输入提交
     - Given 输入框为空
     - When 点击"提交"
     - Then 按钮禁用并提示"请填写内容"
   ```
   规则：可观察的具体行为（不是形容词）；至少一个非正常路径（错误/空/边界/断网）；Then 写用户可见结果
4. **RICE 排序**：(R 触达 × I 影响 × C 信心) / E 工作量，分数高先做。**信心分必须挂钩证据**：只有假设支撑的功能 C 最高打 1
5. **⛔ 范围确认门**：展示 Must 清单，明确问"MVP 我建议就做这几件事…范围会不会太大/太小？有没有 Must 可以砍？"用户调整后确认，落盘 `05-需求分层.md`

## Common Pitfalls

- **Must 塞 10 个**：MVP 做太大是最常见死法——每加一个 Must，问"没有它产品真的不成立吗？"
- **验收场景全是 happy path**：空输入、断网、超长内容才是翻车现场
- **验收标准写形容词**："响应快、体验好"没法判断做完没
- **Won't 空着**：边界和 Must 一样重要，不写清楚范围必然蔓延
- **故事写成功能名**："导出功能"不是用户故事；"作为读者，我希望导出 PDF 以便打印"才是
- **RICE 信心分拍脑袋**：C 分只能来自调研证据，没证据就是 1
- **替用户砍需求**：分层结果 ⛔ 给用户过目，砍什么是用户的决定

## 输出物

- `05-需求分层.md`（含 RICE 排序表 + Won't have 清单，⛔ 用户确认后）
