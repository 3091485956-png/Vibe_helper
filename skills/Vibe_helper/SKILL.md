# Vibe Helper — 从产品想法到落地的一条龙助手

本 skill 把"我想做一个叫 X 的东西"这种模糊输入，逐步收敛成一份可直接开发的产品方案，并在关键节点让用户确认。全程使用中文。

本套件还包含 5 个单点 skill：`product-brief`（问卷+Brief）、`competitive-analysis`（竞品调研）、`user-voice`(用户声音)、`requirements-layering`（需求分层）、`tech-framework`（框架与选型）。它们与全流程读写**同一套编号文件**；用户只要单点产出时直接用它们，本 skill 只在"一条龙"诉求时触发。

## 图例与总原则

- **⛔ 确认门**：必须停下等用户明确确认，不自行跳过。
- **🔶 选择点**：停下摆出选项与推荐，用户一句话拍板（认可 / 增删 / "你定"）。
- **每步先讲为什么**：进入每个阶段时，先用一两句话告诉用户这个阶段为什么存在、它的产出影响后面哪个决策；每次给推荐，理由和依据跟着给。

1. **需求访谈** — 结构化问卷（Mom Test 纪律），补齐产品背景
2. **提示词打磨** — 把问卷结果重写成清晰的产品 brief，⛔ 确认
3. **竞品与开源调研** — GitHub + 全网筛查，🔶 用户确认对标集合
4. **用户声音挖掘** — 竞品评论 + 目标用户真实讨论 → ⛔ 调研后决策门（敢说别做）
5. **需求分层** — MoSCoW + Gherkin 验收标准 + RICE 排序，⛔ 确认范围
6. **框架输出** — 先写"最薄一刀"，再展开产品框架与技术框架
7. **静态原型图** — 高保真可点静态 HTML，⛔ 确认
8. **进入制作** — 范围守卫 + 按依赖顺序开发 + 交付前 checklist

工作目录：在项目根目录建 `./<产品名>/`，所有产出物落盘其中（`00-状态.md`、`01-问卷.md`、`02-brief.md`、`03-竞品分析.md`、`04-用户声音.md`、`05-需求分层.md`、`06-产品框架.md`、`07-技术框架.md`、`prototypes/`、`backlog.md`）。**`00-状态.md` 是滚动状态卡**——全流程的主上下文与一致性锚，规则见 `references/context-assembly.md`。

## 深度档位（流程一开始就确认）

开场先问用户选档，不选就用标准档。**用户选了快速档就不要给标准档的产出**——多做是自嗨，不是负责。

| 档位 | 竞品数 | 用户声音渠道 | 验收场景/故事 | 原型页数 | 适用 |
|---|---|---|---|---|---|
| 快速 | ~5 | 2 | 每故事 2 场景，Must ≤4 | 2 | 周末小工具、先看看可行性 |
| 标准（默认） | 10–15 | 4 | 每故事 2–3 场景，Must 3–6 | 3–6 | 正常新产品 |
| 深度 | 20+ 含间接竞品专章 | 6+ 含中英文 | 每故事 3–5 场景 + 双层 RICE | 5–8 含窄屏 | 认真创业/评审用 |

⛔ 确认门与 🔶 选择点在所有档位都不可省略。快速档唯一例外：Stage 1 出口的状态卡确认与 Brief 确认门合并为一次停顿。

## 中途进入（不是必须从 Stage 1 开始）

先看 `./<产品名>/` 已有哪些文件：**存在的直接复用，不重做**；从第一个缺失阶段进入。**先读 `00-状态.md`**——存在且组装清单未过期（清单中各文档版本 == 该文档当前版本头）就以它为主上下文；缺失而已有 ≥2 份文档、或已过期，先按 `references/context-assembly.md` 重组装再继续。缺前置时按下表补齐（口述即可，不强制补完整文档）：

| 进入点 | 需要 | 缺失时 |
|---|---|---|
| Stage 3 竞品 | 02-brief（或口述定位） | 问 3 个问题：做什么/给谁/核心功能 |
| Stage 4 用户声音 | 03 的确认对标集合 + 用户画像 | 问竞品名 + 目标用户 |
| Stage 5 需求分层 | 02 功能清单（03/04 可选） | 让用户口述功能清单 |
| Stage 6 框架 | 05 需求分层 | 先补 Must 清单 |
| Stage 7 原型 | 06 + 07 | 先过一遍关键页与选型 |
| Stage 8 交接 | 05 + 07 + prototypes/ | 不可跳过，先补齐 |

## 失败模式对照（M 编号从这里来，全文引用需与下表一致）

| # | vibe coding / 新产品常见死法 | 本流程的对策 |
|---|---|---|
| M1 | 一句话直接开写，做出来根本不是想要的 | Stage 1–2：问卷 + Brief ⛔ 确认后才动 |
| M2 | 需求只存在用户脑子里，理解从未被确认 | Brief 确认门，最多 3 轮修正 |
| M3 | demo 一晒就扔：空状态/报错/密钥/部署全没有 | 交付前 checklist + validate.sh 机器自检 |
| M4 | MVP 越做越大，中途加功能改坏旧代码 | 范围守卫：新想法一律进 backlog.md |
| M5 | 明知没人要还陪用户硬做 | 调研后决策门：敢说"别做了" |
| M6 | 无序开发：先画 UI 后定数据层，全部返工 | 最薄一刀 + 严格依赖顺序 |
| M7 | 文档越写越多，后期重点被淹没，文档间悄悄矛盾 | 滚动状态卡 00 + 文档版本链 + 一致性审查 |

## Stage 1 · 需求访谈（问卷）

**为什么**：用户只给了一个名字或一句话，信息严重不足（M1）。**不要**直接跳到竞品搜索。

按 `references/questionnaire.md` 抛问卷：Mom Test 纪律（问过去的行为，不问未来的意愿）、分块、一次 ≤8 题、模糊处追问 1–2 轮。必须拿到：定位、背景动机、目标画像、功能清单（原样记录）、场景、约束偏好、成功指标。快速档只问 4 组核心题。

产出：`01-问卷.md`（带版本头 v1）。

### ⛔ Stage 1 出口 · 状态卡出生

问卷落盘后，按 `references/context-assembly.md` 组装 **00-状态.md v1**（问卷纪要：定位、用户、功能清单原始、约束、成功标准、存疑项），展示给用户并明确问："这是我对问卷的记录——有没有记错的、漏掉的？"用户同意才进 Stage 2；快速档与 Brief 确认门合并为一次停顿。这次确认的是**事实记录**，Stage 2 门确认的是**理解与取舍**，不是重复检查。

## Stage 2 · 提示词打磨（产品 Brief）⛔

**为什么**：让完全不了解背景的工程师看完就懂（M2）。

按 `references/prompt-refinement.md` 把 Stage 1 的回答重写成结构化 Brief：定位、用户、痛点、场景、功能清单、非功能需求、**明确不做**、成功指标。消除一切模糊词。

展示给用户并明确问："以上理解是否准确？有没有要补充或修改的？"

- 用户有补充 → 修改后再确认，最多 3 轮；超过 3 轮改为"列出分歧点让用户逐条拍板"，不死循环
- 用户确认 → 落盘 `02-brief.md`（版本头 v1），并在**同一步**刷新 00-状态.md v2（吸收"明确不做"边界与非功能需求）

**⛔ 未拿到明确确认，禁止进入下一阶段。**

## Stage 3 · 竞品与开源调研

**为什么**：动手前先知道赛道里有什么，避免做出"竞品早就免费覆盖"的东西（M1）。

搜索策略、记录字段、报告结构、好/坏记录对照见 `references/competitive-analysis.md`。要点：多关键词交叉；每个竞品实际打开主页/README；间接竞品一并考虑；报告末尾必写"对本产品的启发"和"本轮盲区"。

**零幻觉纪律**：全程遵守 `references/anti-hallucination.md`——每个链接本轮真实打开过，stars/维护状态当场核对，[实证/推断/假设] 显式标注。

### 🔶 对标选择点

报告落盘后，向用户汇报三样东西：

1. **参照竞品总表**：本轮实际打开看过的名单（不是搜索结果堆砌）
2. **重点对标推荐 2–3 个**，理由只能是：用户重叠度最高 / 功能形态最接近 / 最值得借鉴；同时列出**不推荐**对标的和原因
3. **明确问用户**：
   > 竞品调研做完了，实际参照了这些竞品：【名单】。
   > 我建议重点对标【2–3 个】，理由：【逐个给】；备选【…】。
   > 你有没有自己知道的竞品要补进来？想换重点对标的直接说；不想管就说"你定"。

用户增删 → 补查更新再确认一轮；确认后写入 `03-竞品分析.md` 的"确认对标集合"小节。这个集合是 Stage 4–6 的锚，不再自由发挥。

## Stage 4 · 用户声音挖掘

**为什么**：验证需求是真是假——只有用户自己的转述不可信，公开渠道的真实抱怨才是证据（M5 的前置）。

按 `references/user-research.md`：挖对标竞品的差评/好评 + 目标用户在 Reddit/HN/知乎/V2EX/小红书等的真实讨论。提炼机会点/价值点/空白点，每条附出处链接与行为证据（有没有人在付费、用 workaround、花时间绕过），输出"需求真伪初判"。末尾必写"本轮盲区"。

### ⛔ 调研后的决策门（M5：敢说"别做了"）

Stage 3+4 做完，先停下诚实评估：

- **赛道已死？** 3 个以上成熟、免费、维护活跃的竞品覆盖得很好，且说不清差异化？
- **需求是假的？** 公开渠道几乎零讨论、零抱怨、没人凑合？
- **技术不可行？** 关键依赖根本跑不通？

每个判断标注证据等级并列出盲区；盲区太大就先说"证据不够，建议再查 X"，不许硬给结论。任何一条成立，**必须明确建议**："基于调研，我建议不要做 / 换方向 / 把范围缩到 X"，附证据。不要为了把流程走完硬着头皮陪用户做。

调研支持继续，**先做主组装**：把确认对标集合、需求真伪初判、机会点 top、盲区提示写进 00-状态.md v3（模板见 `references/context-assembly.md`）——这是 Stage 5–8 的主上下文来源。然后进 Stage 5。

## Stage 5 · 需求分层 ⛔

**为什么**：MVP 做太大是最常见的失败原因（M4 的第一道防线）。

以 **00-状态.md 为主上下文**（需要证据细节时按小节回查 03/04，不全文重读），按 `references/requirements-layering.md` 用 MoSCoW 分层：Must 3–6 个，每个写成用户故事（带稳定 ID）+ **≥2 个 Gherkin 验收场景（Given/When/Then，至少一个非正常路径）**；Must 内部用 RICE 排出开发先后；Won't have 明确列出。

**⛔ Must 范围给用户过目**："MVP 我建议就做这几件事…这个范围会不会太大/太小？有没有 Must 可以砍？"确认后落盘 `05-需求分层.md`（版本头记"基于 00-状态@vN"），并在**同一步**刷新 00-状态.md v4：写入带 ID 的 Must 清单、Won't、RICE 顺序。

## Stage 6 · 产品框架 + 技术框架

**为什么**：把"做什么"翻译成"怎么做"，且定死开发顺序防返工（M6）。

以 **00-状态.md v4 为主上下文**（写难点与选型时回查 05 对应故事的完整验收场景，不全文重读），按 `references/framework-output.md`，**先写"最薄一刀"**（一个用户做一件最小的事，从打开到看到结果——写不出 = 还没想清楚 MVP），再展开：

- 产品框架 `06-产品框架.md`：信息架构、用户流程、关键页面元素清单（只列 Must）
- 技术框架 `07-技术框架.md`：架构分层、选型表（选型/理由/备选）、关键难点（参考竞品怎么做）、依赖顺序的开发顺序

选型表给用户过目一次：用户想换就直接改，回"你定"就按推荐走——技术栈是用户偏好，不替用户拍板。06/07 落盘时版本头记"基于 00-状态@v4"。

## Stage 7 · 静态原型图 ⛔

**为什么**：在 0 开发成本下让用户点到、看到、指出"我要的不是这样"，避免视觉返工（M1/M2 的视觉防线）。

按 `references/wireframe.md`：只画 Must 涉及页面，高保真静态 HTML（真实布局/文案/配色，mock 数据写死，页面可点击跳转），输出到 `./<产品名>/prototypes/`，入口 `index.html`。

交给用户后明确请用户：在浏览器点一遍，指出哪里要改/不对/缺东西。**⛔ 用户确认前禁止写真实产品代码**；反馈修改循环直到达成一致。**确认前先跑一致性 checklist**（`references/context-assembly.md`：06 页面 ↔ 05 Must 双向覆盖、Won't 未复活、ID 一致等）；**确认后在同一步刷新 00-状态.md v5**（最薄一刀、选型要点），并 bump 06/07 版本头。

## Stage 8 · 进入制作（交接）

**边界**：本 skill 的产出是文档 + 静态原型，不直接生成最终产品代码。职责是把开工材料备齐、约束写死、交接给执行者（下游 skill 或开发团队），并在交付前核对。

**先看环境里装了哪些建站/全栈/文档类 skill**，按产品形态挑最合适的调用；没有对应 skill 就**不要硬调**——把 `07-技术框架.md` 的开发顺序和交接指令直接交给开发者（或另起会话），交付包本身就是交付物。

### 交接材料

1. `00-状态.md`（**置顶**：一页看懂全局与全部关键决策；组装清单必须与各文档当前版本一致）
2. `02-brief.md`（定位与边界）
3. `05-需求分层.md`（**连同每个验收场景一起传**）
4. `07-技术框架.md`（含最薄一刀和开发顺序）
5. `prototypes/` 整个目录（视觉基准）

**给下游 skill 的指令里必须包含这句硬指令**：

> 只实现 05-需求分层.md 里标注为 Must have 的功能，以及它们对应的验收场景。
> 不要加任何文档里没写的页面、功能、按钮、字段。
> 视觉严格对齐 prototypes/ 目录里的静态原型，不要自由发挥。

### 范围守卫（M4）

开发过程中用户或自己想加新功能：**不许直接做**。追加到 `./<产品名>/backlog.md`，告诉用户"这个放二期"。

### 开发顺序（M6）

严格按 `07-技术框架.md`：骨架可部署 → 数据模型定死 → **最薄一刀端到端打通**（哪怕 UI 丑）→ 补其他 Must → 补空/错/加载态。

### 交付前必过 checklist（M3）

宣布"做完了"之前，逐条过 `references/delivery-checklist.md`：每个验收场景对照打勾（输出验收对照表）、空/错/校验/密钥/部署/README、没有 Must 以外功能。

**任何一条不过，就不算交付。** 制作中发现需求与框架/原型冲突，回到对应文档更新，而不是临时在代码里瞎改。

## Common Pitfalls（agent 执行自查）

- **⛔ 门没停**：没有用户明确确认就进下一阶段。用户催"快点"也要拿到对 Brief/范围/原型/交付的明确"可以"
- **产出只在对话里飘着**：每阶段必须落盘 `./<产品名>/`，用户随时能翻目录
- **调研凭印象**：链接没打开就引用、stars 凭记忆填——违反零幻觉纪律，该段作废重做
- **自检没跑就宣布完成**：⛔ 门放行与交付前必须跑 validate.sh，脚本不过门不算过
- **原型画了 Should/Could 页面**：浪费且诱导范围蔓延
- **用户中途加需求直接做了**：一律进 backlog.md，这是 M4
- **确认死循环**：Brief 修正超 3 轮，改为列分歧点逐条拍板
- **擅自升档**：用户选快速档却给标准档产出——多做了显得勤奋，是自嗨
- **后期全文重读所有文档**（M7）：以 00-状态.md 为主上下文，按小节回查需要的细节
- **状态卡过期/只改卡不改文档**：任何文档 bump 后必须同一步刷新 00；发现矛盾先改文档再重组装，不许用状态卡盖住矛盾
- **新文档不带版本头**：首次落盘即 v1 带版本头，validate.sh 会拦
- **替用户拍板**：做不做、对标谁、砍什么、选什么栈——给选项+推荐+理由，用户定

## 执行原则

- **每阶段产出落盘**；**⛔ 必须真停**；**调研要真做**（真打开仓库看 README/star/commit/issues，真读帖子，关键结论附链接）
- **零幻觉 + 不自嗨**：调研类产出遵守 `references/anti-hallucination.md`——[实证/推断/假设] 标注、链接本轮真实打开、数字不凭记忆、末尾"本轮盲区"、无自我评价、结论强度匹配证据
- **边界要敢砍**：Won't have 和 Must 一样重要；**原型先行**；**验收驱动**（逐场景打勾，不是"感觉差不多"）
- **范围守卫**：新需求进 backlog；**判断权归用户**；**每步先讲为什么**；**不确定就问**，产品方向、目标用户、付费意愿不脑补
