# badcase 台账（AI 轨道交付时随交接包留下）

**为什么**：AI 产品上线后才是主战场。没有台账，badcase 散落在聊天记录和脑子里，修一个坏一个（M9），能力边界永远说不清。本文件在 **Stage 8 交接时创建**（空表 + 规则），落盘为 `./<产品名>/badcase台账.md`，交给开发/运营当产品的代谢系统。

## 记录格式（一行一个 case）

| # | 日期 | 用户输入（原样） | 期望 | 实际 | 环境与版本 | 归因 | 修法 | 状态 |
|---|---|---|---|---|---|---|---|---|
| B1 | | | | | 模型/prompt 版本 | | | 待修 / 已修 / 已回灌 |

- **输入原样保存**：截断、脱敏可以，改写不行——归因要能复现
- **版本必须记**：同一个 case 换模型/prompt 版本可能不复现，不记版本等于没记
- **期望列由人定**：和评测集同一条铁律——AI 可以预填"默认答案（C 级）"，人批准才算数

## 归因分诊表（先归因，再动手）

同一个症状（"答错了"）病因可能在五层，修法与成本完全不同：

| 归因 | 典型症状 | 修法 | 成本 |
|---|---|---|---|
| prompt 问题 | 指令没说清/互相冲突，换个说法就好 | 改 prompt → 跑冒烟子集 | 低 |
| 检索问题 | 捞错/漏了上下文，材料在库里但没进 prompt | 调召回 / 分块策略 / 加 rerank | 中 |
| 模型能力上限 | 换更强模型就好，prompt 怎么改都差 | 升级模型，或**收窄能力边界**（挪进"不保证"并写进 UI 文案） | 高 |
| 数据问题 | 脏数据 / 缺数据 / 数据过期 | 清洗 / 补数据 | 中 |
| 交互设计问题 | 模型没错，产品把输出用错了地方 | 改产品流程与文案 | 中 |

**归因错了就白修**：顺序固定为 复现 → 归因 → 修复 → 回归。模型能力上限类 badcase 的正确修法常常不是修，而是把边界收窄、写进用户看得见的文案——这要同步更新 02-brief 的能力边界。

## 回灌规则（闭环的最后一步）

- 每个"已修"的 badcase，关闭前**必须变成 08-评测方案里的一个新用例**（状态记"已回灌"）
- 冒烟子集优先收录高频 / 高损 badcase
- **未回灌不得关闭**：防"修一个坏一个"

## 边界联动

某类输入长期失败 → 该类输入从 02-brief 能力边界的"适用域"挪进"不保证"，UI 文案同步。评测数据是边界的唯一裁判：**边界不是写出来的，是测出来的。**

## Common Pitfalls

- **badcase 记在聊天记录里**：不落台账 = 不存在
- **不复现就开修**：改完无法验证修没修好
- **修完不回灌**：同一个 case 下个月换个马甲再来一次
- **能力上限硬修**：prompt 救不了模型上限，该收窄边界就收窄——说不保证，好过错了再说
