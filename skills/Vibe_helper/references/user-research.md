# 用户声音挖掘模板

产出语言跟随用户语言：04-用户声音.md 正文用用户的语言，文件名与小节标题保持模板原样。

**结构金标准**：`references/report-examples/金标准-用户痛点调研.md`（用户提供）。痛点呈现格式（定性标题+原话引述+量化数据+行为证据）、五类证据来源、现有工具缺口表、编号数据来源列表，对照它写。注意：金标准范例未带 A/B/C 标注与待核实清单，我们的产出这两样必须带，不得以"像金标准"为由省略。

## 目标

不是写综述，是提炼**可指导产品决策**的洞察。每条痛点要能回答："所以我们产品该多做什么、少做什么？"痛点必须落到去向：进 05 的哪个功能候选，还是进待核实。

## 深度档位

档位管**来源覆盖广度**，不管报告骨架。快速档也要有痛点排序、工具缺口表与数据来源列表，只是渠道少、量化证据可有可无。

| 档位 | 来源类别数 | 范围 |
|---|---|---|
| 快速 | 2 类 | 吐槽平台加 1 类，够做"需求真伪初判" |
| 标准，默认 | 4 类 | 下表前四类 |
| 深度 | 5 类全含 | 加时间线对比，看抱怨是否长期存在；中英文社区都扫 |

## 五类证据来源，按证据硬度排序

1. **学术实证研究（最硬，标准档起必查）**：arXiv、期刊上针对本领域的复现性/可用性/失败率量化研究。一条"X% 的用户遇到 Y"的实证数字，抵一百条单条吐槽。引用必须带论文编号或 DOI，数字当场核对
2. **竞品评论区**：App Store、Google Play、Chrome Web Store、Product Hunt、G2、知乎商品回答
3. **技术社区**：Reddit 相关 subreddit、Hacker News、V2EX、即刻、少数派
4. **中文社区**：知乎、小红书、抖音、微博、B站评论区——用户原话的"关键时刻"多在这里
5. **官方与媒体观察 + 黑客松/workshop 报告（深度档）**：媒体报道、官方调查、高校活动报告，用于交叉验证主观感受；GitHub Issues 与 Discussions 归入此类一并扫，开源竞品的 issue 区是金矿

**搜索词模板**：

- `<竞品名> 缺点 / 吐槽 / 垃圾 / 替代`
- `有没有类似 <竞品名> 但是 <期望改进点> 的`
- `我想要一个能 ___ 的工具`
- `how do you handle <问题> without <竞品>`
- `<领域> 工具 推荐 2026`，看最新对比帖
- `<领域> reproducibility / usability / failure 实证研究`（学术来源检索）

## 痛点呈现纪律

痛点是本报告的正文主体，格式对照金标准"二、复现论文痛点"：

1. **按严重程度排列**，编号痛点1、痛点2……排序依据写进摘要（谁最高频、谁阻塞最狠、有无量化）
2. **每条痛点四件套**：

```markdown
### 痛点N：<定性标题>——<一句冲击性概括>
- 高频引述："..." — <来源链接> [A]
- 量化数据：<研究编号/报告 + 具体数字>。本轮未获得量化数据时明确写"无量化数据"，不许含糊带过
- 行为证据：<有没有人在付费、用 workaround、花时间绕过>
- 对我们的启示 + 去向：<做什么不做什么> → <05 功能候选 / 待核实>
```

3. **标题本身要说人话**：金标准的"环境配置地狱——90%的复现死在依赖版本上"是范本；"环境依赖问题"不是标题
4. 次要场景（如金标准里"写论文痛点"相对"复现痛点"）单独一节简述，不与主场景混排

好例（摘自金标准，补上证据等级即我们的格式）：

> ### 痛点一：环境配置地狱——90%的复现死在依赖版本上 [A：引述+量化双源]
> - 高频引述："90%的代码复现失败源于依赖版本冲突" — <链接> [A]
> - 量化数据：PyTorch 1.8 代码在 2.0+ 环境报错率 93% [A：arXiv:xxxx 当场核对]
> - 行为证据：Docker 公认为金标准但多数学生不会写 [A ×2]
> - 启示：一键环境是基本型需求 → 去向：05 Must 候选

坏例：

> 用户普遍对现有工具不满意，希望有更好的产品。

"普遍"是多少？来源在哪？标题无信息量，无量化，无去向。

## 提炼方法：看行为证据，不看口头意愿

Mom Test 的原则同样适用于读帖子：**用户做了什么，如用 workaround、付费、花时间绕过，比用户说了什么，如"希望有个 X"，可信得多**。

把搜到的帖子按主题归类，而不是逐条罗列。重点找：

- **反复出现的抱怨**：3 个以上独立来源提到同一个痛点即高优先级机会
- **量化佐证**：吐槽有没有学术实证或统计数字背书，有则痛点等级直接上调
- **用户自发夸的点**：用户愿意为什么掏钱、为什么留下来
- **workaround**：用户现在在用什么凑合方案，那就是我们的直接竞争对手。有人在付钱或花时间凑合即需求为真，标 [A]；只有人嘴上说想要、没人在凑合即需求存疑，标 [C·模型推测]
- **付费意愿信号**："要是有 X 我愿意付 $Y/月"

## 现有工具缺口表

必产小节：目标用户现在能用的所有方案，一行一个，说清每个"能做什么"与"关键缺口"。这张表三处复用：差异化定位的证据（缺口即空隙）、Stage 4 劝退门的输入（成熟方案全覆盖即"赛道已死"信号）、05 需求地图的素材。

| 现有方案 | 能做什么 | 关键缺口 |
|---|---|---|
| <竞品/通用工具/手动方案> | | |
| 通用大模型（AI 赛道必列） | | |

至少覆盖：确认对标集合里的竞品、通用大模型、最常见的手动凑合方案。

## 需求真伪初判

汇总判断，证据结构化：

- 独立来源数 / 量化证据有无 / 行为证据有无 → 初判：真需求 / 存疑 / 假需求，附证据等级
- 判"真"至少要行为证据；只有口头意愿的按存疑处理

## 纪律

- 严格遵守 `anti-hallucination.md`：引用的每个帖子与评论必须本轮真实打开过，转述与原帖不符即违规；论断标 A/B/C，B 带推理链
- **每条洞察至少 2 个独立来源**才算数，单条轶事标为"待验证"；学术数字必须当场核对原文
- 不要编评论、不要编数字。搜不到就写"本轮未覆盖，建议后续补充 X 社区"；查不到量化就写"本轮未获得量化数据"
- 区分"用户说要的"和"用户真正需要的"。用户常会提错误的解决方案，记录时区分他们的**抱怨**和他们的**建议**
- 文档末尾必写"待核实清单"：盲区即哪些渠道没覆盖、哪些结论证据最薄，加推测即 C 级逐条附验证路径
- **痛点必须有去向**：每条痛点要么指向 05 功能候选，要么进待核实清单，不许写完就沉底
