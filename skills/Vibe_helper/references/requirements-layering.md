# 需求分层模板（MoSCoW + Gherkin 验收标准 + RICE 排序）

## 原则

- **MVP 要小**：Must have 控制在 3–6 个功能，能在合理时间内做完
- 每个功能可独立交付、可验证
- 来源标注：[问卷] / [竞品] / [用户声音]，方便回溯
- 写不出用户故事 = 没想清楚，回去想

## 深度档位

| 档位 | Must 数 | 验收场景 | RICE |
|---|---|---|---|
| 快速 | ≤4 | 每条 2 个场景 | 不打分 |
| 标准（默认） | 3–6 | 每条 2–3 个场景 | Must 内部打分排序 |
| 深度 | 3–6 | 每条 3–5 个场景 | Must + Should 都打分，输出排序理由 |

## 用户故事格式

```
作为 <角色>，我希望 <做某件事>，以便 <获得某种价值>。
```

每条 Must 带一个**稳定 ID**（M-F1、M-F2…，首次写 05 时分配并同步进 00-状态.md，此后不再改号）。后续 06/07 引用功能一律带 ID。

## 验收标准：Gherkin 场景（关键）

**每个 Must have 用户故事必须带 ≥2 个验收场景**，用 Gherkin（Given/When/Then）写。
这些标准会在开发完成后逐条对照打勾——写得含糊 = 最后没法判断做完没。

格式：

```
- 验收标准：
  - 场景 1：空输入提交
    - Given 输入框为空
    - When 点击"提交"
    - Then 提交按钮禁用，并提示"请填写内容"
  - 场景 2：正常提交
    - Given 输入了 10 字以上的内容
    - When 点击"提交"
    - Then 跳转 result.html，URL 带任务 id
```

❌ 反例（模糊，无法判断做完没）："页面好看"、"体验流畅"、"响应快"、"系统运行良好"
✅ 正例见上——每个场景能一眼判断对错，不需要主观评价。

每条验收标准必须满足：

1. Given/When/Then 是**可观察的具体行为**，不是形容词
2. 每个故事至少一个**非正常路径**场景（错误/空/边界/断网），不要全写 happy path
3. Then 写的是用户可见的结果，不是内部实现

### AI 类 Must：验收改造（AI 轨道时）

AI 功能的输出是非确定的、分级的——Gherkin 管不了"摘要好不好"，硬写 Then 就形同虚设（M8）。规则：

- **工程路径照写 Gherkin**：提交、报错、空态、加载、降级——这些是确定性的，照旧
- **输出质量不写 Gherkin，改写评测引用**：
  ```
  - 质量验收：见 08-评测方案.md 环节 <名称>，通过线 <N%>——评测集整集跑完达线才算过
  ```
- 每条 Must 标注 **类型：常规 / AI**；AI 类 Must 没有评测引用 = 该条验收不完整，validate.sh 会拦

## RICE 排序（Must 内部决定开发先后）

MoSCoW 决定"做不做"，RICE 决定"先做谁"。对每个 Must 打分：

| 字母 | 含义 | 打分 |
|---|---|---|
| R | 触达：多大概率/多高频触达目标用户 | 1–3 |
| I | 影响：对成功指标的拉动 | 1–3 |
| C | 信心：来源证据强度（用户声音 A 级证据多 → 高） | 1–3 |
| E | 工作量：预估人日 | 1–10 |

**RICE = (R × I × C) / E**，分数高的先做。信心 C 必须和调研证据挂钩：只有 [假设] 支撑的功能 C 最高打 1。

## 分层定义

| 层 | 含义 | 数量参考 |
|---|---|---|
| Must | 没有它产品不成立，MVP 必做 | 3–6 个 |
| Should | 重要，但 MVP 缺了也能跑 | 5–10 个 |
| Could | 锦上添花，排期看资源 | 越多越好 |
| Won't | 本期明确不做，写下来防 scope creep | 明确列出 |
